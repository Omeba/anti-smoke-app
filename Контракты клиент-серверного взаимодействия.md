Взаимодействие клиента и сервера проходит через REST API. Для каждого эндпоинта указаны метод, путь, данные запроса и условия получения ответов.

## Правило доступа

Пользоваться приложением (вернее, его основным функционалом) можно только после входа. Для защиты от спама все запросы к API, кроме запросов входа и `GET /v1/app-config`, требуют действующий JWT в заголовке `Authorization: Bearer <JWT>`.

Для защищённых эндпоинтов сервер проверяет JWT до обработки запроса. Если токен отсутствует, недействителен или просрочен, сервер возвращает `401 Unauthorized` без тела с заголовком `WWW-Authenticate: Bearer`.

# 1. Аутентификация

Для четырёх эндпоинтов входа JWT не требуется. Параметров пути и строки запроса нет. Клиент отправляет тело с заголовком `Content-Type: application/json`.

**На согласование:** сроки действия JWT, сколько будет жить кэш конфига и аватарок, а также рейтлимит

## 1.1 По почте

### 1.1.1 `POST /v1/auth/email/login`

Запрашивает код подтверждения по электронной почте.

**Тело запроса**

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `email` | `string` | Да | Адрес электронной почты. |

Пример запроса

```json
{
  "email": "user@example.com"
}
```

**Ответы**

| HTTP-статус | Условие | Тело ответа |
| --- | --- | --- |
| `200 OK` | Сервер принял запрос на отправку кода по электронной почте. | Без тела. |

| `429 Too Many Requests` | С устройства поступило больше трёх запросов за минуту. | Без тела. |
| `503 Service Unavailable` | Сервер временно недоступен. | Без тела. |


| `400 Bad Request` | Некорректный JSON или ошибка в обязательных полях. | Без тела. |
| `403 Forbidden` | Код неверен или больше не действителен. | Без тела. |
| `429 Too Many Requests` | С устройства поступило больше трёх запросов за минуту. | Без тела. |
| `503 Service Unavailable` | Сервер временно недоступен. | Без тела. |

Тело ответа `200 OK`

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `token` | `string` | Да | JWT, выданный после проверки кода. |

# 2. Данные команды

## 2.1 `GET /v1/app-config`

Возвращает текущую опубликованную конфигурацию приложения. Эндпоинт доступен до входа и выдаёт одну и ту же конфигурацию всем клиентам.

**Запрос**

Параметров пути, строки запроса и тела нет. JWT не требуется. Клиент отправляет `If-None-Match`, если у него есть сохранённая копия конфигурации и её `ETag`.

```http
GET /v1/app-config
If-None-Match: W/"app-config-42"
```

**Ответы**

| HTTP-статус | Условие | Заголовки и тело |
| --- | --- | --- |
| `200 OK` | `If-None-Match` отсутствует или текущий `ETag` не совпадает с переданным. | `Content-Type: application/json`, текущий `ETag`, `Cache-Control: public, max-age=60, stale-while-revalidate=120`. Тело содержит полный набор конфигурации. |
| `304 Not Modified` | Текущий `ETag` совпадает с переданным в `If-None-Match` по правилам слабого сравнения. | Текущий `ETag` и та же политика `Cache-Control`, что у `200`. Без тела. |
| `503 Service Unavailable` | Сервер или опубликованная конфигурация временно недоступны. | `Cache-Control: no-store`. Без тела. |

**Версия конфигурации и кэширование**

- Сервер формирует слабый `ETag` из ревизии опубликованной конфигурации, например `W/"app-config-42"`. Ревизия меняется при любом изменении выдаваемых данных. Сервер публикует данные и их ревизию вместе.
- При `200` клиент заменяет локальную копию и её `ETag`. При `304` клиент использует сохранённое тело и обновляет метаданные кэша из ответа.
- Клиентские и общие кэши могут использовать ответ 60 секунд без проверки и ещё до 120 секунд при фоновой проверке. После этого для повторного использования требуется успешная проверка.

JSON ответа `200` содержит следующие поля. Все поля верхнего уровня обязательны.

1. `statistics` — объект с константами для расчёта статистики:
   - `relapseNicotineMg` (`number`) — доза никотина, принятая для расчёта в день срыва, в миллиграммах.
   - `cigarettesPerPack` (`integer`) — число сигарет в пачке, больше нуля.
   - `minutesPerCigarette` (`number`) — минуты на одну сигарету.
   - `streakGoalDays` (`integer`) — порог цели серии в днях, больше нуля.
2. `achievements` — массив объектов с обязательными полями `id`, `title`, `category`, `rewardText` (все `string`) и `threshold` (объект). У порога два обязательных поля: `metric` (`string`, код показателя) и `value` (`number`, порог в единицах показателя).
3. `motivationalQuotes` — массив строк с мотивирующими цитатами.
4. `toolbox` — массив объектов с обязательными полями `id`, `title`, `howItHelps` (все `string`), `tags` (`string[]`) и `durationMinutes` (`integer`, длительность в минутах).
5. `questionnaire` — массив опубликованных и видимых вопросов. Каждый вопрос содержит обязательные поля `id` и `text` (оба `string`), `type` (`single_choice`, `multiple_choice` или `text`) и `required` (`boolean`, обязателен ли ответ пользователя). Для вопросов с выбором обязательно поле `options` с непустым массивом объектов `{ "id": string, "label": string }`. Для вопросов типа `text` поле `options` отсутствует.
6. `avatarEmojis` — массив доступных для выбора эмодзи в порядке отображения. Каждый элемент содержит обязательные поля `id` (`string`, стабильный идентификатор) и `label` (`string`, подпись для интерфейса и экранного диктора). Клиент подставляет `id` в путь `GET /v1/avatar-emojis/{id}/image` для загрузки картинки.
7. `documents` — массив из двух объектов (политика конфиденциальности и условия использования). Каждый содержит обязательные поля `id` (`privacy_policy` или `terms_of_use`), `title` (`string`), `contentMarkdown` (`string`, опубликованный текст), `version` (`integer`, версия текста) и `requiredAcceptanceVersion` (`integer`, минимальная версия, которую должен подтвердить пользователь). При любой правке текста увеличивается `version`. Если требуется повторное подтверждение, сервер также устанавливает `requiredAcceptanceVersion` в новую `version`. Клиент запрашивает подтверждение, если сохранённое подтверждение отсутствует или его версия ниже `requiredAcceptanceVersion`.
8. `uiTexts` — объект с обязательными словарями `errors` и `hints` типа `Record<string, string>`. Ключи — стабильные коды сообщений, значения — тексты для интерфейса.

Массивы идут в порядке отображения. Идентификаторы элементов сохраняются при переименовании и изменении порядка. Ответ включает общую конфигурацию приложения и больше ничего.

## 2.2 `GET /v1/avatar-emojis/{id}/image`

Возвращает изображение эмодзи для аватара. Клиент может загружать картинки по мере отображения вариантов в списке. Тот же путь используется для отображения выбранного аватара по его идентификатору.

**Авторизация** — требуется `Authorization: Bearer <JWT>`.

**Запрос**

| Параметр пути | Тип | Обязательный | Описание |
| --- | --- | --- | --- |
| `id` | `string` | Да | Стабильный идентификатор эмодзи из `avatarEmojis` или из сохранённого выбора пользователя. |

Тело и параметры строки запроса отсутствуют. Если клиент сохранил изображение и его `ETag`, он отправляет эту метку в необязательном заголовке `If-None-Match`. При первой загрузке или при отсутствии копии клиент опускает этот заголовок.

```http
GET /v1/avatar-emojis/sprout/image
Authorization: Bearer <JWT>
If-None-Match: W/"avatar-emoji-sprout-3"
```

**Ответы**

| HTTP-статус | Условие | Заголовки и тело |
| --- | --- | --- |
| `200 OK` | Изображение доступно, и `If-None-Match` отсутствует или не совпадает с текущим `ETag`. | `Content-Type: image/png`, текущий `ETag`, `Cache-Control: private, no-cache`. Тело содержит байты PNG. |
| `304 Not Modified` | Изображение доступно, и `If-None-Match` совпадает с текущим `ETag` по правилам слабого сравнения. | Текущий `ETag`, `Cache-Control: private, no-cache`. Без тела. |
| `401 Unauthorized` | JWT отсутствует, недействителен или просрочен. | `WWW-Authenticate: Bearer`, без тела. |
| `404 Not Found` | Изображение с таким идентификатором отсутствует. | Без тела. |
| `503 Service Unavailable` | Сервер или хранилище изображений временно недоступны. | Без тела. |

Сервер проверяет JWT и наличие изображения до сравнения меток. Слабый `ETag` меняется при обновлении изображения по тому же `id`. При `200` клиент сохраняет PNG и метку вместе. При `304` он использует сохранённый PNG и обновляет метаданные кэша. Политика `private, no-cache` разрешает хранить изображение в клиентском кэше и требует проверки перед повторным использованием.

Если администратор убирает эмодзи из каталога, вариант исчезает из `avatarEmojis`. Сервер продолжает отдавать картинку по тому же `id`, пока она используется в профилях.

# 3. Аккаунт

После подтверждения способа входа клиент получает JWT и вызывает `GET /v1/account`. Если аккаунт уже создан, клиент загружает сохранённые данные. Если сервер отвечает `404`, клиент открывает регистрацию и отправляет её данные через `POST /v1/account` после заполнения. JWT связывает оба запроса с подтверждённой учётной записью для входа, даже если профиль ещё не создан.

## 3.1 `POST /v1/account`

Создаёт аккаунт и сохраняет данные регистрации на сервере. Параметров пути и строки запроса нет. Обязательные заголовки — `Authorization: Bearer <JWT>` и `Content-Type: application/json`.

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `name` | `string` | Да | Имя до 100 символов после обрезки пробелов по краям. Допустимы буквы, пробелы и дефисы. Имя должно содержать хотя бы одну букву. |
| `birthDate` | `string` | Да | Дата рождения в формате `YYYY-MM-DD`. Дата должна существовать, год — от 1900, возраст — от 18 полных лет. |
| `formOfAddress` | `string` | Да | Код выбранного обращения. |
| `quitStage` | `string` | Да | Код выбранного этапа отказа от курения. |
| `quitDate` | `string\|null` | Да | Дата отказа в формате `YYYY-MM-DD` или `null`, если на выбранном этапе дата ещё не задана. |
| `nicotineUseMethods` | `string[]` | Да | Коды способов потребления никотина в порядке выбора при регистрации, без повторов. Этот порядок используется в опроснике. |
| `avatarEmojiId` | `string` | Нет | Идентификатор эмодзи из `avatarEmojis` в `GET /v1/app-config`. Если поле опущено, сервер назначает стартовый эмодзи. |

Email, телефон, VK ID и Яндекс ID сервер заполняет из подтверждённых данных входа. Одноимённые поля в теле запроса считаются ошибкой. Допустимые коды обращения и этапов отказа, условия обязательности даты и допустимость пустого списка способов потребления нужно согласовать со сценарием регистрации. Коды в примере условные.

```json
{
  "name": "Марк",
  "birthDate": "1992-08-15",
  "formOfAddress": "informal",
  "quitStage": "quit",
  "quitDate": "2026-11-20",
  "nicotineUseMethods": ["cigarettes", "hookah"],
  "avatarEmojiId": "fox"
}
```

| HTTP-статус | Условие | Заголовки и тело |
| --- | --- | --- |
| `201 Created` | Сервер сохранил аккаунт. | `Location: /v1/account`, `Content-Type: application/json`, `Cache-Control: no-store`. Тело совпадает по схеме с ответом `200` метода `GET /v1/account`. |
| `400 Bad Request` | Некорректный JSON или недопустимые поля и значения. | Без тела. |
| `401 Unauthorized` | JWT отсутствует, недействителен или просрочен. | `WWW-Authenticate: Bearer`. Без тела. |
| `409 Conflict` | Для подтверждённой учётной записи уже сохранён аккаунт. | Без тела. Клиент загружает сохранённые данные через `GET /v1/account`. |
| `503 Service Unavailable` | Сервер временно не может обработать запрос. | Без тела. |

Сервер создаёт аккаунт и привязывает его к учётной записи входа атомарно. Повторный или параллельный запрос после успешного создания получает `409` и не изменяет профиль. Если клиент не получил ответ на отправку, он может проверить результат через `GET /v1/account`.

## 3.2 `GET /v1/account`

Возвращает сохранённые данные аккаунта текущего пользователя. Сервер определяет аккаунт по JWT. Параметров пути, строки запроса и тела нет. Обязательный заголовок — `Authorization: Bearer <JWT>`.

| HTTP-статус | Условие | Заголовки и тело |
| --- | --- | --- |
| `200 OK` | Для подтверждённой учётной записи есть аккаунт. | `Content-Type: application/json`, `Cache-Control: no-store`. Тело содержит данные аккаунта. |
| `401 Unauthorized` | JWT отсутствует, недействителен или просрочен. | `WWW-Authenticate: Bearer`, `Cache-Control: no-store`. Без тела. |
| `404 Not Found` | Для подтверждённой учётной записи ещё нет сохранённого аккаунта. | `Cache-Control: no-store`. Без тела. |
| `503 Service Unavailable` | Сервер временно не может получить данные. | `Cache-Control: no-store`. Без тела. |

Все поля ответа `200` обязательны. `name`, `birthDate`, `formOfAddress`, `quitStage`, `quitDate` и `nicotineUseMethods` имеют те же типы, что и при регистрации.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `string` | Стабильный идентификатор аккаунта, назначенный сервером. |
| `email` | `string\|null` | Текущий подтверждённый адрес или `null`. При смене адреса здесь остаётся прежний адрес до подтверждения нового. |
| `avatar` | `object` | Текущая аватарка. Для эмодзи — `{ "type": "emoji", "emojiId": string }`, изображение загружается по `GET /v1/avatar-emojis/{id}/image`. Для фото — `{ "type": "photo", "url": string }`, где `url` — адрес изображения. Фото сохраняется через § 3.3. |

```json
{
  "id": "account_123",
  "name": "Марк",
  "email": "user@example.com",
  "birthDate": "1992-08-15",
  "formOfAddress": "informal",
  "quitStage": "quit",
  "quitDate": "2026-11-20",
  "nicotineUseMethods": ["cigarettes", "hookah"],
  "avatar": { "type": "emoji", "emojiId": "fox" }
}
```

## 3.3 `PATCH /v1/account`

Сохраняет изменения на экране «Мой аккаунт». Сервер определяет аккаунт по обязательному заголовку `Authorization: Bearer <JWT>`. Параметров пути и строки запроса нет.

**Запрос `application/json`**

Тело содержит хотя бы одно из полей таблицы. Пропущенные поля сохраняют текущие значения. Неизвестные поля и значения `null` отклоняются.

| Поле | Тип | Описание |
| --- | --- | --- |
| `name` | `string` | Новое имя. Действуют правила регистрации из § 3.1. |
| `birthDate` | `string` | Новая дата рождения в формате `YYYY-MM-DD`. Действуют правила регистрации из § 3.1. |
| `avatarEmojiId` | `string` | Идентификатор доступного эмодзи из `GET /v1/app-config`. Выбранный эмодзи заменяет текущую аватарку. |

Пример изменения имени

```json
{
  "name": "Маркус"
}
```

**Запрос `multipart/form-data`**

Заменяет текущую аватарку фотографией. Единственная часть `photo` содержит исходный файл в формате JPG, PNG или HEIC размером до 10 МБ (10 000 000 байт), с разрешением от 200×200 px. Необязательная часть `crop` с типом `application/json` задаёт выбранный квадрат как `{ "x": integer, "y": integer, "size": integer }`. Координаты отсчитываются от верхнего левого угла изображения после применения его ориентации. Квадрат должен целиком помещаться в изображение и иметь сторону не менее 200 px. Если `crop` опущен, сервер использует наибольший квадрат по центру. Сервер проверяет исходный файл, сохраняет квадратное изображение с разрешением не более 1024×1024 px и обновляет аватарку после успешной записи изображения.

**Ответы**

| HTTP-статус | Условие | Тело |
| --- | --- | --- |
| `200 OK` | Изменения сохранены. | Полный аккаунт по схеме § 3.2 в `application/json`. |
| `400 Bad Request` | Некорректное тело, недопустимое поле или значение, неизвестный эмодзи, повреждённое фото, слишком низкое разрешение или неверная область обрезки. | Без тела. |
| `401 Unauthorized` | JWT отсутствует, недействителен или просрочен. | Без тела. Заголовок `WWW-Authenticate: Bearer`. |
| `404 Not Found` | Аккаунт ещё не создан. | Без тела. |
| `413 Content Too Large` | Файл превышает лимит размера. | Без тела. |
| `415 Unsupported Media Type` | Неподдерживаемый тип тела или формат фото. | Без тела. |
| `503 Service Unavailable` | Сервер или хранилище фото временно недоступны. | Без тела. |

Все ответы содержат `Cache-Control: no-store`. Если ответ потерялся, клиент может сверить результат через `GET /v1/account`.

## 3.4 Смена email

Смена адреса выполняется двумя запросами. Оба требуют `Authorization: Bearer <JWT>` и `Content-Type: application/json`. Параметров пути и строки запроса нет. Все ответы содержат `Cache-Control: no-store`.

### 3.4.1 `POST /v1/account/email-change`

Принимает `{"email":"mark.new@example.com"}`. Поле `email` обязательно. Адрес должен отличаться от текущего, содержать `@` и домен с точкой, без пробелов. Сервер отправляет на новый адрес шестизначный код, действующий 60 секунд. Успешная повторная отправка или запрос для другого адреса аннулирует предыдущий код. До подтверждения для профиля, входа, уведомлений и восстановления доступа действует прежний адрес.

| HTTP-статус | Условие | Тело |
| --- | --- | --- |
| `202 Accepted` | Запрос на отправку кода принят. | Без тела. |
| `400 Bad Request` | Адрес отсутствует, имеет недопустимый формат или совпадает с текущим. | Без тела. |
| `409 Conflict` | Адрес занят другим аккаунтом. | Без тела. |
| `429 Too Many Requests` | Повторная отправка пока ограничена. | Без тела. `Retry-After` содержит число секунд до следующей попытки. |

### 3.4.2 `POST /v1/account/email-change/confirm`

Принимает `{"email":"mark.new@example.com","code":"042731"}`. Оба поля обязательны. `code` — строка ровно из шести цифр. Код проверяется для текущего аккаунта и адреса последнего принятого запроса. Сервер повторно проверяет доступность адреса и атомарно обновляет профиль и привязку email для входа. Использованный код аннулируется.

| HTTP-статус | Условие | Тело |
| --- | --- | --- |
| `200 OK` | Адрес подтверждён и сохранён. | Полный аккаунт по схеме § 3.2 в `application/json`. |
| `400 Bad Request` | Ошибка формата запроса или кода. | Без тела. |
| `403 Forbidden` | Код неверен, просрочен или больше не действителен. | Без тела. |
| `409 Conflict` | Адрес уже занят другим аккаунтом. | Без тела. |
| `429 Too Many Requests` | Превышен лимит попыток проверки. | Без тела. `Retry-After` содержит число секунд до следующей попытки. |

Оба метода также возвращают `401 Unauthorized` с заголовком `WWW-Authenticate: Bearer` при ошибке JWT, `404 Not Found` при отсутствии аккаунта и `503 Service Unavailable` при временном сбое. Эти ответы возвращаются без тела. Порог попыток и интервал повторной отправки нужно согласовать отдельно.
